# 1. Поточна мета проєкту RFID

Кінцева практична ціль — використовувати Nordic ID на складі замість фотографування бірки:

1. працівник підносить / наводить Nordic ID на RFID-бірку;
2. натискає фізичний курок;
3. наша веб-сторінка отримує RFID EPC;
4. сторінка визначає потрібний робочий номер;
5. запис автоматично потрапляє в основну таблицю приймання / загальну базу;
6. користувач одразу бачить підтвердження, що запис прийнятий.

На найближчий етап **не намагаємося ідеально повторити фірмову Android-програму**. Потрібен стабільний робочий обхід через уже встановлений Nordic ID RFID Wedge Service і веб-сторінку.

# 2. Що вже доведено

## 2.1. RFID-залізо Nordic ID працює нормально

Фірмова програма CC4Scanner на цьому самому девайсі стабільно читає RFID, у тому числі:
- одну мітку;
- кілька міток;
- мітки на робочій дистанції приблизно 10–12 см у наших тестах.

Отже базова проблема **не в самому RFID-модулі, не в антені і не в Chrome як такому**.

## 2.2. CC4Scanner підключається до RFID reader напряму через NUR API

На екрані фірмової програми зафіксована помилка:

`Could not connect to RFID reader. Please close and restart the app.`  
`java.lang.Exception: NurApi.connect(): connection failed`

Це прямий практичний доказ, що CC4Scanner використовує `NurApi.connect()` і напряму підключається до Nordic ID RFID reader.

## 2.3. Wedge і CC4Scanner конкурують за один і той самий reader

Коли запущений `Nordic ID RFID Wedge Service`, CC4Scanner може не підключитися до RFID reader і показує `NurApi.connect()` failure.

Після:
- зупинки Wedge;
- або перезавантаження Nordic ID;

фірмова програма знову працює нормально.

### Практичне правило

**Для фірмової програми CC4Scanner:**
- `Wedge service = STOP`.

**Для наших веб-тестів / веб-роботи:**
- запускаємо Wedge;
- CC4Scanner у цей момент не використовуємо.

Не намагатися працювати обома шляхами одночасно.

## 2.4. Фірмова програма має щонайменше два різні RFID-профілі

Користувач багаторазово перевірив фактичну поведінку:

- `Scan All Tags` — читає всі RFID-мітки, які бачить reader;
- `Scan CCTag6 only` — фактично повертає одну мітку за сканування.

Технічні NUR-параметри цих режимів у звичайному UI CC4Scanner не показані. Висновок: вони, ймовірно, задаються всередині програми.

# 3. Архітектура двох способів читання

## 3.1. Фірмова програма

`CC4Scanner → NUR API → Nordic ID RFID reader → RFID tags`

CC4Scanner безпосередньо керує reader: може запускати Inventory, завершувати його, фільтрувати теги, вибирати режим single/multi та інші NUR-параметри.

## 3.2. Наша поточна веб-схема

`RFID tags → Nordic ID RFID reader → RFID Wedge Service → keyboard/wedge input → Chrome → наша HTML-сторінка`

Важливо: **HTML/JavaScript зараз не керує RFID reader напряму.** Веб-сторінка лише обробляє те, що Wedge уже передав як клавіатурний ввід.

# 5. Відомі RFID EPC

Відомі тестові коди:

1. `33161403D0000785000E3103`
2. `33161403D0000785002CB739`

Wedge передає повний 24-символьний EPC одним `INPUT`, після чого приходить `Enter` і веб-сторінка робить `SCAN_COMMIT`.

Коли Wedge вирішив передати результат, передача відбувається дуже швидко — приблизно 10–20 мс від data-producing trigger event до `INPUT`.

### Правило даних

Завжди зберігати повний raw EPC як канонічне сире RFID-значення. Не вигадувати і не виправляти символи.

# 6. Що показали журнали і відео

## 6.1. Focus браузера не є головною причиною

V2.0 FOCUS GUARD підтвердив, що під час актуальних тестів input мав focus. Отже поточна нестабільність не пояснюється просто втратою focus.

## 6.2. Довге утримання курка не допомагає

Довгий hold створює багато повторних:

`KEYDOWN key="Unidentified"`

приблизно кожні ~50 мс, але це не означає нові успішні RFID reads.

Для тестів використовувати **короткі натискання**.

## 6.3. Wedge може передати кілька RFID у межах одного Inventory

Зафіксовані пари різних EPC з інтервалами приблизно 80–190 мс.

Приклади:
- `...0E3103`
- через ~80–190 мс `...2CB739`

Це означає, що один inventory-cycle може знайти дві RFID-бірки і Wedge послідовно віддати обидва EPC у браузер.

## 6.4. Є регулярна проблема з повторними/порожніми trigger-циклами

У багатьох тестах видно характерний патерн приблизно:

`натискання без EPC → наступне натискання з EPC → без EPC → з EPC ...`

Тобто Wedge не дає нам ідеального `1 фізичне натискання = 1 EPC`.

На найближчому робочому етапі **не витрачаємо більше часу на ідеальне виправлення цієї поведінки**.

# 7. Перевірені Wedge settings

Початковий / відомий стан:

- `Trigger behavior = RFID`
- `Re-trigger action = Cancel current operation`
- `Long trigger press = OFF`
- `RFID tag output mode = Hex string`
- `Character set = UTF-8`
- `RFID operation type = Inventory`
- `Maximum number of tags = 0 (any)`
- `RFID inventory timeout seconds = 0 (infinite)`

Перевірялися зміни по одному параметру:

### A. `Re-trigger action`
`Cancel current operation → Restart current operation`

Не вирішило головну проблему.

### B. `RFID inventory timeout`
`0 → 1 second`

Суттєвого покращення не дало. У приблизному порівнянні успішність залишилася близько 50% фізичних trigger-циклів.

### C. `Maximum number of tags`
`0 → 1`

Не прибрало дивну черговість. Також у журналі все одно були дуже близькі послідовні EPC двох різних бірок.

### Висновок

Не продовжувати хаотично крутити Wedge settings. Поточний Wedge достатній як транспорт EPC до браузера, але не повторює поведінку CC4Scanner один-в-один.

---

# 8. Безпечний стан після експериментів

Якщо CC4Scanner перестає читати:

1. повернути Wedge settings до початкового стану;
2. `Wedge service = STOP`;
3. повністю закрити CC4Scanner;
4. відкрити CC4Scanner заново;
5. якщо не допомогло — перезавантажити Nordic ID.

Цей recovery уже перевірений: після reboot фірмова програма знову працювала нормально.

# 9. Рішення на поточний етап — ОБХІД Wedge-проблеми у веб-логіці

## Головне рішення

**Не чекаємо Android/NUR API рішення. Не намагаємося зараз зробити Wedge ідеальним.**

Для робочого використання завтра веб-сторінка має працювати за правилом:

> **Після фізичного початку сканування прийняти перший валідний EPC, а всі наступні EPC цього самого короткого scan-cycle тимчасово заблокувати / проігнорувати.**

Мета — отримати практичну поведінку максимально близьку до:

`одне робоче сканування → один робочий RFID номер`

навіть якщо Wedge усередині віддасть другий EPC або повтор.

## Принцип FIRST-TAG LOCK

Планована логіка веб-сторінки:

1. сторінка готова до нового scan-cycle (`ARMED`);
2. приходить перший валідний 24-char EPC;
3. EPC негайно приймається;
4. сторінка переходить у `LOCKED`;
5. усі додаткові EPC у цьому ж короткому циклі ігноруються;
6. через визначену умову сторінка знову переходить у `ARMED` для наступного реального сканування.

### Умова розблокування — спочатку найпростіша і найбезпечніша

Для першої робочої версії використати коротке **cooldown-вікно** після першого прийнятого EPC.

Стартове значення для тесту: приблизно **500–800 мс**.

Чому:
- другий EPC тієї самої inventory-серії у наших логах часто приходив через ~80–190 мс;
- 500–800 мс повинно відсікти другий тег того самого пакета;
- наступне нормальне фізичне натискання користувача зазвичай буде пізніше.

Точне значення підібрати тестом, не вгадувати.

## Додатковий захист від дублювання

Окремо від FIRST-TAG LOCK зберегти duplicate guard:
- однаковий EPC не повинен двічі створити один і той самий робочий запис за дуже короткий час;
- логування сирих подій при цьому можна залишити для діагностики.

# 10. План роботи ДО ЗАВТРА

## Етап 1 — нова тестова веб-версія

З V2.0 FOCUS GUARD зробити наступну контрольовану версію, умовно:

**V2.1 — FIRST TAG LOCK**

Не ламати V2.0. Створити окремий файл / нову версію.

Додати:
- FIRST-TAG LOCK;
- видимий лічильник `Accepted`;
- видимий лічильник `Blocked`;
- у TEST-журнал події `RFID_ACCEPTED` і `RFID_BLOCKED`;
- зберегти весь raw EPC;
- не викликати Android keyboard;
- не додавати ручні елементи, які забирають focus.

## Етап 2 — короткий контрольний тест

Перевірити:
- одна бірка — серія коротких натискань;
- дві бірки поруч — за один scan-cycle у робочу логіку має пройти тільки **перший** EPC;
- журнал має показати, що другий EPC прийшов, але був `BLOCKED`, а не втрачений безслідно.

Якщо це стабільно працює — FIRST-TAG LOCK вважається робочим обходом Wedge.

## Етап 3 — підключення до загальної бази

Після проходження TEST:

1. взяти accepted EPC;
2. визначити з EPC потрібний робочий ідентифікатор за затвердженим правилом;
3. записати скан у **загальну робочу таблицю / основний потік Mottak**;
4. зберігати також raw EPC для аудиту;
5. не торкатися Camera-потоку більше, ніж потрібно для спільної таблиці.

Перед production-write спочатку перевірити точну схему `public.mottak_scans` і не змінювати її навмання.

## Етап 4 — робочий UI на Nordic ID

Для завтрашнього практичного використання екран має бути максимально простий:

- великий статус `READY`;
- після успіху — великий `OK` + прийнятий номер;
- якщо EPC заблокований як другий у циклі — не лякати користувача технічним повідомленням;
- автоматичне повернення в READY;
- мінімум дрібного технічного тексту;
- технічний журнал лишається в Supabase, а не заважає працівнику на екрані.

# 12. Довгостроковий план — Android / NUR API

Це **не поточний пріоритет**, але зберігається як правильний майбутній напрямок.

Коли буде час і буде підтверджено, що на Nordic ID дозволено встановлення власного APK:

1. зробити маленький Android RFID-модуль на Nordic ID NUR API;
2. напряму керувати Inventory;
3. мати власні режими:
   - Single tag;
   - Multi tag;
4. керувати power / timeout / filters / trigger logic через NUR API, якщо підтримано конкретним hardware/SDK;
5. передавати готовий EPC у нашу веб/серверну частину;
6. прибрати залежність від keyboard Wedge.

Це дозволить наблизитися до архітектури CC4Scanner:

`наша Android-програма → NUR API → RFID reader → наша база/UI`

Але цей етап переноситься на пізніше.
