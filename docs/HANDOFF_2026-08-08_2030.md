Версія, яку показувала TEST-сторінка наприкінці роботи: `products.js v1.2.2 · 7 aktive`.

### Зафіксовані фізичні правила

**Bunner**

```text
1 stabel = 10 Bunner
1 Bunner = 4 CC Post
1 stabel = 40 CC Post
```

**Hyller x30**

```text
1 sett = 1 Bunner + 30 Hyller + 4 CC Post
```

**Hyller x60**

```text
1 sett = 1 Bunner + 60 Hyller + 4 CC Post
```

**Forlengere korte**

```text
1 vogn = 1 Bunner + 4 CC Post
+ фактична кількість Hyller, введена складом
+ фактична кількість Forlengere, введена складом
```

**Forlengere lange** — така сама логіка, як короткі.

**Forlengere plast**

```text
1 одиниця = 1 eske
без Bunner
без Hyller
без CC Post
```

**CC Post** зараз є розрахунковою складовою комплектів. Окремого власного складського руху для CC Post поки немає.

## 5. Критична причина, знайдена 08.08.2026 о 20:19

Проблема була не в тому, що UT Lager не зберігав дані.

Фактичні дані `Hyller` і `Forlengere` правильно потрапляли в `ut_test_extra_confirmations`, але UT Kontor будував видимі фактичні підсумки через **другий окремий RPC-запит** після основного завантаження замовлення.

Через це могло бути:

```text
основне замовлення вже оновлено
але другий progress-запит / UI-шар ще старий або не встиг оновитися
```

Тому стару рампу можна було побачити правильно після ручного refresh/fix, але нове замовлення знову показувало тільки базові числа.

### Root fix

Створена Supabase migration:

```text
20260808181911 ut_test_persist_confirmed_extra_totals
```

В `ut_test_orders` тепер зберігаються автоматично синхронізовані поля:

- `confirmed_hyller_korte`
- `confirmed_forlengere_korte`
- `confirmed_korte_complete`
- `confirmed_hyller_lange`
- `confirmed_forlengere_lange`
- `confirmed_lange_complete`

Увімкнені тригери:

- `ut_test_extra_confirmations_sync_totals`
- `ut_test_order_items_sync_totals`

`ut-kontor-history-visuals.js` оновлений до **v1.8.0** і тепер бере фактичні totals прямо з рядка `ut_test_orders`; для видимих totals другий progress RPC більше не є необхідним.

Останні ключові GitHub commits цього root-fix:

- `8a90b3108dcf4b29e60f47174ee5216ee44e5435` — Fix TEST UT Kontor totals to use persisted confirmed extras
- `7abf752d2db64f38804fff69067f6c0e03c39de9` — Bump TEST UT Kontor to persisted live totals

## 9. НАЙВАЖЛИВІШЕ: що перевірити наступним

Не робити новий patch одразу.

Треба створити **нову TEST-рампу після root-fix** і пройти її від початку до кінця:

```text
1. TEST UT Kontor
   → створити абсолютно нову рампу
   → замовити H30/H60 + korte/lange (+ plast за бажанням)

2. TEST UT Lager
   → вибрати/зарезервувати Bunner/H30/H60
   → для кожного korte/lange ввести різні фактичні числа
   → Bekreft усі нові одиниці
   → перевести На рампу

3. Повернутися в TEST UT Kontor
   → НЕ міняти дані руками
   → перевірити, що сама нова рампа автоматично показує правильні:
      Bunner total
      Hyller total
      Forlengere korte actual
      Forlengere lange actual
      CC Post
```

Це головний acceptance test. Якщо він проходить — root-fix вважається підтвердженим.

Якщо не проходить, діагностика повинна бути такою:

```text
UI input
→ RPC request
→ ut_test_extra_confirmations
→ persisted fields у ut_test_orders
→ GET ut_test_orders
→ render UT Kontor
```

Не підправляти цифри конкретної рампи вручну. Знайти, на якому саме переході дані перестають збігатися.

## 10. Правила роботи, які не змінювати

1. **Production не змінювати** під час TEST-налагодження.
2. Не робити ручні виправлення конкретних замовлень як основне «рішення» багу.
3. Після кожного виправлення перевіряти **нове замовлення**, а не тільки стару рампу.
4. Спочатку TEST → потім GREEN → потім явне підтвердження користувача → production.
5. Старі стабільні файли/снапшоти не видаляти без потреби.
6. Кожна значна сторінкова зміна має мати видиму версію й точний час оновлення.
7. Зберігати бізнес-правила комплектів у центральному `products.js`, а не дублювати хаотично по сторінках.
8. Не вважати `x30/x60` розміром стопки; це назва/тип комплекту Hyller.
9. На картках замовлення фактичні Hyller/Forlengere коротких/довгих показувати **тільки в Totalt**.
10. CC Post показувати **тільки в Totalt**, поки він залишається derived/display component.
