# 1. Практична мета

Найближча робоча ціль — **вже завтра використовувати Nordic ID у роботі замість фотографування бірок**.

Робочий сценарій має виглядати так:

1. працівник наводить Nordic ID на RFID-бірку;
2. коротко натискає фізичний курок;
3. RFID Wedge передає EPC у Chrome;
4. наша постійна веб-сторінка приймає **тільки перший валідний EPC** цього короткого циклу;
5. усі наступні EPC, що прилетіли від того самого короткого сканування, для робочої операції блокуються;
6. accepted EPC перетворюється / зіставляється з робочим номером, потрібним системі Mottak;
7. запис після TEST потрапляє в загальну базу Mottak;
8. користувач одразу бачить простий результат `OK` і номер;
9. сторінка автоматично готова до наступного сканування.

**Зараз не намагаємося ідеально повторити фірмову Android-програму.** Потрібно зробити стабільний практичний обхід через існуючий Nordic ID RFID Wedge Service + нашу веб-сторінку.

Native Android / NUR API залишаємо як окремий майбутній етап, коли буде час.

Користувач:

## 3.2. Асистент читає журнал

Якщо користувач пише:

- `дивись журнал`
- `журнал`
- `перевір журнал`

асистент повинен одразу перевірити останню Nordic ID session у Supabase TEST-журналі і дуже коротко сказати:

- скільки blocked RFID;
- які EPC прийшли;
- які були інтервали;
- чи спрацювала поточна логіка.

Не змушувати користувача вручну переносити журнал.

## 3.3. Журнал зберігає більше, ніж бачить робочий UI

Навіть якщо робочий екран блокує другий EPC, TEST-журнал повинен зберегти його як технічну подію, наприклад:

Це важливо для подальшого аналізу.

Робоча операція використовує лише accepted EPC.

# 5. Що доведено про Nordic ID і RFID

## 5.1. Сам RFID-reader і антена працюють

Фірмова програма CC4Scanner на цьому самому Nordic ID читає RFID добре.

Перевірено:

- читання однієї мітки;
- читання кількох міток;
- дві мітки поруч;
- робоча дистанція приблизно 10–12 см у проведених тестах.

Тому проблему не треба пояснювати просто «поганим RFID-залізом».

## 5.2. У CC4Scanner фактично є два різні режими

Користувач перевірив це багато разів:

- ліва панель / `Scan All Tags` → читає всі мітки, які бачить reader;
- права панель / `Scan CCTag6 only` → у фактичній роботі повертає одну мітку за сканування.

Не сперечатися з цим спостереженням у наступних розмовах — воно перевірене користувачем неодноразово.

Напис `CCTag6 only` сам по собі не розкриває всю внутрішню технічну логіку; фактична поведінка правого режиму — single-tag.

## 5.3. Низькорівневі параметри CC4Scanner приховані

У звичайному UI CC4Scanner користувач не бачить:

- TX power;
- NUR inventory параметрів;
- session/target;
- Q;
- точного timeout;
- точного алгоритму single-tag;
- інших внутрішніх параметрів reader.

Сильний висновок: фірма задає ці параметри всередині програми / її конфігурації, а користувачу показує лише готові режими.

# 6. Найважливіше відкриття — CC4Scanner використовує NUR API напряму

Коли Wedge був активний, у CC4Scanner зафіксовано повідомлення:

`Could not connect to RFID reader. Please close and restart the app.`

та технічну помилку:

`NurApi.connect(): connection failed`

Це є прямим практичним свідченням того, що CC4Scanner намагається підключитися до RFID reader через `NurApi.connect()`.

Практична архітектура фірмової програми:

`CC4Scanner → NUR API → integrated RFID reader → RFID tags`

Фірмова програма керує reader напряму, тому потенційно може сама:

- запускати Inventory;
- зупиняти Inventory;
- використовувати фільтри;
- задавати RF-параметри;
- реалізовувати single-tag та multi-tag сценарії.

Точний внутрішній код CC4Scanner ми не знаємо, тому не вигадувати конкретні NUR settings без доказів.

---

# 7. Наша поточна веб-архітектура

Наш шлях зараз інший:

`RFID tags → Nordic ID reader → Nordic ID RFID Wedge Service → keyboard input → Chrome → наша веб-сторінка`

Важливе обмеження:

> HTML/JavaScript зараз **не керує самим RFID reader**. Він лише отримує те, що Wedge уже вирішив віддати як клавіатурний ввід.

Тому веб-сторінка не може напряму сказати NUR reader:

- «прочитай рівно одну мітку»;
- «зупини Inventory після першої»;
- «зміни TX power»;
- «використай такий session/target».

Зате сторінка може надійно контролювати **що робити з EPC після того, як Wedge його передав**. Саме це і використовуємо зараз.

---

# 8. Wedge і CC4Scanner не використовувати одночасно

Практично встановлено, що Wedge і CC4Scanner можуть конкурувати за той самий integrated reader.

Коли Wedge активний, CC4Scanner може отримати `NurApi.connect()` failure.

## Для CC4Scanner

- `Wedge Service = STOP`;
- відкрити CC4Scanner;
- якщо не підключається — закрити/відкрити;
- якщо все одно не працює — reboot Nordic ID.

## Для нашої веб-сторінки

- CC4Scanner не використовувати;
- запустити RFID Wedge Service;
- відкрити нашу Nordic ID WORK page у Chrome.

## Recovery, якщо фірмова програма перестала читати

1. повернути Wedge settings до базового стану;
2. зупинити Wedge Service;
3. закрити CC4Scanner;
4. відкрити його знову;
5. якщо потрібно — reboot.

Цей recovery уже фактично спрацював.

# 9. Відомі базові Wedge settings

Початковий / безпечний відомий стан:

- `Automatic service start = OFF`
- `Trigger behavior = RFID`
- `Re-trigger action = Cancel current operation`
- `Long trigger press = OFF`
- `RFID tag output mode = Hex string`
- `Character set = UTF-8`
- `Append newline = Line feed (0x0A)`
- `PREFIX = empty`
- `POSTFIX = empty`
- `RFID operation type = Inventory`
- `Maximum number of tags = 0 (any)`
- `RFID inventory timeout seconds = 0 (infinite)`
- barcode timeout, який бачили в меню: `10 sec`

У GS1-налаштуваннях на екрані були активні включення serial number / check digit / application identifier. Не змінювати їх без конкретної потреби.

# 10. Які Wedge зміни вже перевірені

## 10.1. Re-trigger action

Перевірено:

`Cancel current operation → Restart current operation`

Результат: головну проблему не виправило.

Не повторювати цей тест без нової конкретної причини.

## 10.2. RFID inventory timeout

Перевірено:

`0 → 1 sec`

Результат: суттєвого покращення не було. У приблизному порівнянні success rate залишився близько половини trigger-cycle.

Не вважати timeout головною причиною.

## 10.3. Maximum number of tags

Перевірено:

`0 → 1`

Результат:

- не прибрало регулярну дивну черговість empty/success;
- у журналі все одно були дуже близькі послідовні EPC двох різних тегів.

Тому не робити висновок, що Wedge `Maximum tags = 1` дає нам гарантований single-tag режим.

## 10.4. Висновок по Wedge settings

Не витрачати зараз час на хаотичне перемикання параметрів.

Wedge для поточної задачі розглядаємо як **транспорт EPC у браузер**, а його недоліки обходимо веб-логікою.

# 11. Що браузер реально отримує від Wedge

Відомі тестові EPC:

1. `33161403D0000785000E3103`
2. `33161403D0000785002CB739`

Повний EPC має 24 символи.

Типова успішна послідовність подій:

`KEYDOWN key="Unidentified"`

→ `BEFOREINPUT`

→ `INPUT` з **повним 24-char EPC одним шматком**

→ `Enter`

→ `SCAN_COMMIT`

Коли Wedge дійсно передає RFID, дані зазвичай приходять дуже швидко — приблизно через 10–20 мс після відповідної data-producing trigger-події.

Повний raw EPC зберігати як канонічне сире значення. Не вигадувати символи і не «виправляти» RFID-код.

# 12. Що показали журнали та відео

## 12.1. Focus не є головною проблемою

`V2.0 FOCUS GUARD` показав, що input може стабільно мати focus, але дивна RFID поведінка все одно залишається.

Отже не повертатися до нескінченного лікування focus як до основної причини.

## 12.2. Довге утримання курка не допомагає

При hold з’являються повторні:

`KEYDOWN key="Unidentified"`

приблизно кожні ~50 мс.

Це не означає нове корисне RFID-читання.

Для практичної роботи і тестів використовувати **коротке натискання курка**.

## 12.3. Wedge може віддати два різні EPC дуже близько

У журналах зафіксовано пари різних EPC з інтервалами приблизно:

- 78 мс
- 82 мс
- 83 мс
- 87 мс
- 88 мс
- 91–95 мс
- 168–190 мс

Тобто після одного apparent scan action Wedge може послідовно віддати два теги.

Це ключова причина для FIRST TAG LOCK.

## 12.4. Патерн empty/success

У контрольованих тестах часто спостерігався патерн приблизно:

`trigger без EPC → наступний trigger з EPC → trigger без EPC → trigger з EPC ...`

Механізм усередині Wedge точно не доведений, тому не називати без доказів його внутрішній state machine.

Практичний висновок лише один: Wedge не гарантує нам ідеальне `1 physical press = 1 EPC`.

## 12.5. Тест Restart + timeout 0

У відповідному сегменті було приблизно:

- 39 `Unidentified` downs;
- 22 commits;
- обидва відомі теги;
- приблизно 50% успішних apparent press/bursts.

Також підтверджені два теги в дуже близькому часовому вікні.

## 12.6. Тест timeout 1 sec

У відповідному сегменті було приблизно:

- 70 `Unidentified` downs;
- 38 commits;
- tag A: 21;
- tag B: 17;
- приблизно 52% success bursts.

Порівняно з timeout 0 суттєвого покращення немає.

## 12.7. Тест Maximum tags = 1

У session `nid-20260809163145587-mjkgc7` зафіксовано:

- 46 `Unidentified` downs;
- 27 commits;
- tag `...0E3103`: 18;
- tag `...2CB739`: 9.

І навіть при `Maximum number of tags = 1` було щонайменше 7 дуже чітких пар різних EPC з розривом приблизно 83–182 мс.

Тому цей setting не дав нам потрібного single-tag результату.

- прийняти;
- позначити `RFID_ACCEPTED`;
- показати користувачу;
- перейти в `LOCKED`.

Усі наступні валідні EPC, які приходять у короткому lock-вікні:

- **не використовувати як новий робочий скан**;
- позначити `RFID_BLOCKED` у TEST-журналі;
- не відправляти в production Mottak як окремий прийом.

Після завершення lock-вікна:

- автоматично повернутися в `READY`.

## 14.2. Початкове lock-вікно

Для першого тесту використовувати приблизно **500–800 мс**; стартова реалізація може бути близько 600 мс.

Причина: другий тег у наших тестах зазвичай прилітав через ~80–190 мс, тому 600 мс повинен перекрити цей burst із запасом.

Це початкове значення для тесту, а не священна константа. Після журналу його можна зменшити/збільшити.

## 14.3. Не покладатися поки на точний physical trigger counter

`Unidentified` events можуть повторюватися при hold і не завжди однозначно відповідають одному фізичному натисканню.

Тому перша робоча FIRST TAG LOCK версія повинна бути проста і time-based.

Пізніше можна додати edge-detection trigger counter окремим тестом, якщо це буде потрібно.

# 15. Яким має бути робочий UI Nordic ID

Nordic ID має маленький portrait screen. Робоча сторінка повинна бути максимально проста.

Бажана поведінка:

`READY`

→ користувач сканує

→ `OK`

→ великий робочий номер / EPC або потрібна частина

→ короткий feedback

→ `READY`

Не виводити технічний журнал на основний робочий екран.

Не провокувати Android keyboard popup.

Не додавати зайві кнопки, які можуть забрати focus.

Технічний raw RFID можна показувати одним рядком у компактному debug-блоці, якщо він ще потрібен під час TEST.

# 16. Перехід з TEST у загальну базу Mottak

Після того як FIRST TAG LOCK підтверджено журналом:

1. визначити/перевірити правильний робочий номер із EPC;
2. перевірити актуальну production schema;
3. accepted RFID записувати в загальну таблицю Mottak;
4. blocked RFID у production не писати;
5. blocked події залишати лише в TEST diagnostic log;
6. зберегти існуючі production правила статусів, дублів та складу;
7. не ламати Camera flow.

Відомий production target у поточній архітектурі — `public.mottak_scans`.

Відоме правило продукту: робочий tag ID у production пов’язаний із `lower_number`, але перед інтеграцією завжди перевірити актуальну реалізацію в коді/БД.

Мета цього етапу:

> **Nordic ID повинен створювати той самий корисний запис у загальній системі, який до цього доводилося отримувати через фотографування/Camera flow.**

# 17. Android / NUR API — ПІЗНІШЕ

Майбутній правильний технічний шлях може бути:

`наш Android app → NUR API → RFID reader`

Це потенційно дозволить отримати той самий рівень контролю, який має CC4Scanner:

- direct Inventory control;
- single/multi modes;
- RF power;
- filters;
- stop conditions;
- інші NUR parameters.

Але зараз цей шлях **відкладений**, бо немає часу.

Також ще не перевірено, чи корпоративний Nordic ID дозволяє встановлювати наш APK.

Якщо пізніше буде потрібно, спочатку легально перевірити:

- чи дозволено встановлення APK;
- чи є Play Store / unknown sources;
- чи доступний USB debugging / ADB.

Не обходити MDM або корпоративні обмеження.

Fallback для глибокої діагностики пізніше:

`Windows PC → USB → ADB → Chrome DevTools`

# 19. Що НЕ робимо далі

Не робимо без конкретної нової причини:

- повтор Restart vs Cancel тільки заради повтору;
- повтор timeout 0 vs 1;
- повтор Maximum tags 0 vs 1;
- нескінченні focus зміни;
- довге утримання trigger як «лікування»;
- створення нового HTML-файлу для кожної дрібної версії;
- одночасний запуск Wedge і CC4Scanner;
- випадкові production зміни;
- Android app прямо зараз.
